# 雀魂麻将大模型微调训练方案（DGX Spark / Qwen3.8-27B）

日期：2026-11-21。状态：调研完成，方案设计，待用户确认后实施。

## 〇、追加调研：微调耗时与 flash-next 可微调性（2026-11-21 二轮）

### Q1：Qwen3.8-27B 微调要多久

基于 DGX Spark 实测锚点外推（**不是猜的**）：

| 锚点 | 数据 |
|---|---|
| GB10 实测（8B LoRA, seq4096, batch2×4） | **1.21 s/step** |
| 同机 5000 行专利推理（seq4096） | **101 分钟** |
| GB10 vs H100 | 约 **1/3 速度**（H100 0.45~0.55 s/step）|

我们的样本只有 ~250 token（远短于 4096），序列缩短后 step time 按固定开销占比折算：

| 数据量 | 步数（eff-batch16, 1 epoch） | 27B bf16 LoRA | 27B 4bit QLoRA |
|---|---|---|---|
| 5,000 条（MVP） | 312 | **约 9 分钟** | 约 7 分钟 |
| 20,000 条 | 1,250 | **约 34 分钟** | 约 27 分钟 |
| 50,000 条（全量） | 3,125 | **约 85 分钟** | 约 68 分钟 |

**结论：27B 全量微调约 1~1.5 小时**，加上环境编译（DeltaNet kernel 首次 JIT 约 3~5 分钟）、合并权重、导出 GGUF（约 3~5 分钟）、部署切换，总停机窗口约 **2 小时**。这远快于直觉——因为我们的样本极短，且 1 epoch 足够（领域格式微调不需要多轮）。

> 注：这是基于公开实测锚点的线性外推，真实值需跑一次 smoke train 校准。环境已装好（mjtrain: torch2.11+cu130 / unsloth 2026.11.9 / transformers5.15.1 / trl1.15.0），随时可实测。

### Q2：Qwen3.8-flash-next 有可微调的参数吗

**有，但本机跑不动。** 二轮调研修正了一轮的判断：

- Qwen3.8-Flash-Next 官方于 2026-08 开源了**完整 BF16 safetensors 权重**（131 分片，约 **360GB**），许可证 qwen-community-1.0 **明确允许微调**。
- 结构：125B MoE 主体（6B 激活）+ 51B n-gram 嵌入 + 4B MTP，每 token 只激活 6B。
- 当前部署的 `iq3_s` 79GB GGUF 是它的量化版，不可直接微调；但**原权重存在**。

为什么排除：

| 障碍 | 数据 |
|---|---|
| 权重大小 | 360GB BF16，本机 121.7GB 内存装不下 1/3 |
| 最小量化 | 社区最小 GGUF 仍 72.5GB，且量化格式不可微调 |
| FP8 版 | 也 133GB+，超内存 |
| n-gram 嵌入 | 51B 独立表，训练时需常驻，进一步挤压 |
| 激活参数 | 6B/token 虽少，但 MoE 训练需更新大量专家参数 |

**唯一可行路径**：QLoRA 只微调专家层 + offload n-gram 到 CPU，技术风险高、收益不明确（我们的任务是"选一张牌"，不需要 125B 的通用能力）。

### 修正后的基座选型建议

新增一个更务实的候选：**Qwen3.8-4B-Distill**（Community 蒸馏版，Apache 2.0，9.34GB，safetensors，qwen3_5 架构）。

| 基座 | 权重 | 微调耗时(5万条) | 推理速度 | 适用 |
|---|---|---|---|---|
| Qwen3.8-4B-Distill | 9.3GB | **约 13 分钟** | 最快(~0.3s) | **MVP 首选**：验证数据/流程 |
| **Qwen3.8-27B** | 55.6GB | **约 85 分钟** | 快(~1s) | **生产首选**：能力/速度平衡 |
| Flash-Next 125B | 360GB | 不可行 | 中 | 排除 |
| 2.4T | 1.4TB | 不可行 | — | 排除 |

**建议两步走**：先用 4B 跑通全流程（数据生成→训练→导出→部署→评测，半天内完成），确认提分有效后，再用 27B 做正式版（多花 1.5 小时）。这样避免"花 55GB 下载 + 2 小时停机"后发现数据方案有问题。

## 一、结论

**可以做，但需要换模型、停服训练、再切回服务。** 核心结论：

| 问题 | 答案 |
|---|---|
| 服务器能微调吗 | 能。DGX Spark / GB10 / 121.7GB 统一内存 / 2.8TB 空闲，官方支持微调到 70B |
| 最新参数最高的可微调 Qwen | **Qwen3.8-2.4T-A95B**（2026-08 开源，2.4T 总参/95B 激活）——但本机装不下 |
| 实际最优选择 | **Qwen3.8-27B**（dense, Apache 2.0, safetensors），QLoRA 16~19GB，训练快、可导出 GGUF |
| 当前部署的模型能微调吗 | **不能**。`qwen3.8-flash-next-iq3_s` 是 79GB GGUF IQ3 量化，无 safetensors 原权重 |
| 训练库装不了怎么办 | 服务器直连清华 pypi 可用（已验证 HTTP 200）；仅模型权重需本机下载后 SFTP 中转 |
| 多久能出第一版 | 数据准备 1~2 天，训练约 2~4 小时（取决于数据量），评测半天 |

## 二、服务器实测条件

```
主机：spark-7976，aarch64，Ubuntu 24.04
GPU：NVIDIA GB10（Blackwell，CC 12.1），统一内存 121.7GB，FP4 1 PFLOPS
可用内存：51.9GB（当前模型服务占用约 54GB，训练前需停服释放）
磁盘：2.8TB 空闲，inode 充足
CUDA：13.0；thenv 环境 torch 2.11.0+cu128（可用）
网络：清华 pypi 通；HF / hf-mirror 不通；conda envs 目录可写
```

**关键约束**：

1. 必须停掉当前 8080 服务才能用满内存训练（服务占 54GB）。训练期间桌面端不可用。
2. GGUF 是推理格式，不能微调。必须拿 HF safetensors 原权重。
3. Qwen3.8 是 `qwen3_5` 架构 + 混合 DeltaNet 注意力，需要较新 unsloth/transformers v5，且 LoRA target 要动态发现（旧教程的 q/k/v_proj 命名不适用）。
4. 4-bit 在 DeltaNet 上有已知问题，建议 `load_in_16bit=True` 走 bf16 LoRA（27B 峰值约 70GB，本机 121GB 可容纳）。

## 三、模型选型详解

| 模型 | 参数 | 可微调性 | 判断 |
|---|---|---|---|
| Qwen3.8-2.4T-A95B | 2.4T / 95B 激活 | 理论可，权重 ~1.4TB | **排除**：内存差 11 倍，训练需多机 TB 级显存 |
| Qwen3.5-397B-A17B | 397B / 17B 激活 | 理论可 | **排除**：QLoRA 需 >250GB，超官方 70B 上限 |
| Qwen3.8-27B | 27B dense | 官方支持，Apache 2.0 | **推荐**：QLoRA 16~19GB / bf16 LoRA ~70GB |
| Qwen3.6-35B-A3B | 35B MoE | 可 | 备选：MoE 训练复杂，不优先 |
| 当前 IQ3_S | ~32B 量化 | 不可 | 无原权重 |

**为什么不用更大的**：微调的价值在于注入"雀魂决策习惯"，这不是参数量问题，而是数据分布问题。27B 经过领域微调后，在这类封闭决策任务上可以逼近甚至超过通用大模型（历史数据：受限决策下开思考只 +2 点，说明通用推理能力对"选一张牌"边际价值很低）。

## 四、训练数据设计（核心）

### 4.1 设计原则

1. **答案必须可验证**：用 ExactSolver（本地精确求解器）+ 规则事实生成标准答案，不靠人工主观标注。
2. **覆盖决策全维度**：牌效率、防守、攻守权衡、打点、鸣牌、立直判断、终局。
3. **输入格式对齐生产**：与当前 Jev/structured 模式的 prompt 完全一致，微调后才能无缝替换。
4. **输出极简**：只输出一张牌 + 极简理由（≤12字），保证快速响应。
5. **难度分层 + 对抗样本**：包含高置信简单题、低置信攻守难题、易错陷阱题。

### 4.2 数据规模与构成

目标 **50,000 条**训练样本（可先做 5,000 条 MVP 验证流程）：

| 类别 | 数量 | 答案来源 | 说明 |
|---|---|---|---|
| 牌效率弃牌 | 15,000 | ExactSolver | 随机合法手牌，向听/进张算最优弃牌 |
| 防守（立直威胁） | 10,000 | 安全事实规则 | 现物>筋>字牌>无筋中张，多立直取共同安全 |
| 攻守权衡 | 8,000 | 规则+求解器 | 南4局点差/巡目/听牌形态决定攻或守 |
| 打点/役种 | 5,000 | 规则+求解器 | 宝牌、役牌、门清、立直的价值取舍 |
| 鸣牌判断 | 4,000 | 规则 | 吃碰杠的时机与役种破坏代价 |
| 立直判断 | 3,000 | 规则 | 是否立直、振听风险 |
| 终局/顺位 | 3,000 | 规则 | 流局、点棒、顺位目标 |
| 多立直极限 | 2,000 | 事实规则 | 三家立直共同安全、无共同安全的处理 |

### 4.3 单条样本格式

采用与生产 prompt 对齐的对话格式（JSONL）：

```json
{
  "messages": [
    {"role": "system", "content": "你是雀魂麻将决策模型。只输出一个牌名和一句≤12字理由，格式：牌名|理由"},
    {"role": "user", "content": "手牌(14张)：1m 2m 3m 4m 5m 6m 7m 8m 9m 2p 3p 4p 5p 4z\n当前向听：0\nA=4z（0向听，40张进张）\nB=9m（0向听，38张进张）\n立直家：right\nright牌河：1z\n宝牌指示牌：5z\n轮到你出牌。"},
    {"role": "assistant", "content": "4z|进张最广且现物安全"}
  ]
}
```

### 4.4 数据生成流水线

```
1. 牌山模拟器：随机发牌（13/14张），随机副露，随机牌河/立直状态
   → 保证物理合法（每种牌≤4张，考虑副露可见牌）
2. ExactSolver 核算：向听、进张、弃牌候选（本地已有，0.1s/局）
3. build_safety_facts：现物/筋/共同安全（本地已有）
4. 决策规则引擎：按类别套用攻守/打点/鸣牌规则，产出标准答案
5. 质量校验：
   - 弃牌必须在手牌中
   - 防守题必须落在安全集
   - 牌效率题必须等于 Solver 最优或并列最优
   - 去重、难度分层、训练集/验证集 9:1 划分
6. 导出 JSONL（train.jsonl / eval.jsonl）
```

### 4.5 关键：用现有资产做数据飞轮

已有的 59 场景基准 + 历史 47 题 A/B 数据可直接作为**高难度验证集**。
每次微调后用同一基准评测，确保不退化、可对比。

## 五、训练方案

### 5.1 环境准备（服务器）

```bash
# 1. 建独立环境（不停当前服务）
conda create -n mjtrain python=3.12 -y
conda activate mjtrain

# 2. 清华源装训练库（已验证可达）
pip install -i https://pypi.tuna.tsinghua.edu.cn/simple \
  --no-deps unsloth unsloth_zoo peft trl accelerate datasets bitsandbytes
pip install -i https://pypi.tuna.tsinghua.edu.cn/simple transformers==5.15.1

# 3. 模型权重：本机下载 → SFTP 中转 → 服务器
#    unsloth/Qwen3.8-27B（safetensors，约 55GB）
```

**本机中转流程**（实测本机可访问 hf-mirror.com HTTP 200 与 ModelScope HTTP 302，服务器两者都不通）：
1. 本机下载（`HF_ENDPOINT=https://hf-mirror.com`）：
   ```bash
   HF_ENDPOINT=https://hf-mirror.com huggingface-cli download unsloth/Qwen3.8-27B \
     --include "*.safetensors" "*.json" --local-dir ./Qwen3.8-27B
   ```
   备选：ModelScope `modelscope download qwen/Qwen3.8-27B`
2. SFTP 中转到服务器（paramiko 分块上传，带断点续传）：
   `user@10.201.137.10:/home/user/models/qwen38-27b/`
3. 内网 SFTP 速度预计 50~100MB/s，55GB 约 10~20 分钟

**训练库无需中转**：服务器直连清华 pypi 已实测 HTTP 200。

### 5.2 训练配置

```python
# Qwen3.8 是 qwen3_5 架构 + 混合 DeltaNet，用 FastModel 而非 FastLanguageModel
from unsloth import FastModel
model, processor = FastModel.from_pretrained(
    model_name="/home/user/models/qwen38-27b",
    max_seq_length=1024,       # 单条样本短，1024 足够
    load_in_4bit=False,        # DeltaNet 上 4bit 有问题
    load_in_16bit=True,        # bf16 LoRA
)
# LoRA target 必须动态发现（DeltaNet 不用 q/k/v_proj 命名）
targets = discover_lora_targets(model)  # in_proj/out_proj/ba_proj/conv + MLP
model = FastModel.get_peft_model(model, r=32, lora_alpha=32, target_modules=targets)

# 超参
SFTConfig(
    num_train_epochs=1,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=8,   # 有效 batch 32
    learning_rate=2e-5,
    warmup_steps=50,
    max_steps=2000,                  # MVP 先 2000 步验证
    bf16=True,
)
```

### 5.3 训练后处理

1. 合并 LoRA → 全权重
2. 导出 GGUF（q8_0 / q4_k_m），交给 strata 加载
3. 更新 strata 配置 `model_name` 指向新 GGUF，重启服务
4. 桌面端无需改动（API 兼容）

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| Qwen3.8 新架构训练坑多（DeltaNet/视觉塔） | 先跑 Unsloth 官方 Qwen3.8 教程的 smoke test，再上自有数据 |
| 微调反而退化（灾难性遗忘） | 保留 20% 通用指令数据混训；LoRA rank 不要过大；每 500 步存 checkpoint 评测 |
| 训练期间服务中断 | 停机窗口安排在使用低峰；训练完再切回 |
| 数据分布与实战不符 | 用真实截图识别结果生成部分样本；上线后收集难例回流 |
