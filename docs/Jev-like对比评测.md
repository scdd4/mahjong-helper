# Jev-like vs 当前方案：全面对比评测

日期：2026-11-21。数据来自 59 场景基准（与生产同口径的事实注入）与真实截图端到端测试。

## 一、方案说明

**Jev-like**：用现有 Spark（strata 0.1.59 + qwen3.8-flash）实现 Jev 的 System One 决策语义：
- 候选弃牌映射到单 token A-N，`allowed_token_ids` 锁死 → 结构上不可能输出候选外的牌
- `logprobs` 一次前向读出全部候选的概率分布 → top1 概率即置信度
- 关思考（Jev 是 System One，封闭决策空间已取代 CoT），非流式单请求
- 用户只看到"打哪张牌"一张牌，无大段分析

**当前方案 v1.9.5（fast）**：关思考 + 自回归生成 JSON（discard/reason/wait_plan/risk），靠"牌不在手"事后兜底幻觉。

## 二、核心对比

| 指标 | Jev-like | 当前 fast (v1.9.5) | 差异 |
|---|---|---|---|
| 59 场景准确率 | **81%**（48/59） | 85%（50/59） | -4 点 |
| 模型段中位延迟 | **1.24s** | 1.94s | **快 36%** |
| 结构化幻觉 | **不可能**（token 锁死） | 靠事后兜底 | 根本性改进 |
| 概率/置信度 | **有**（可分支） | 无 | 新增能力 |
| 输出内容 | 一张牌 | 牌+理由+前瞻 | 更简洁 |
| 网络请求 | 1 次 | 1 次 | 相同 |
| 需要训练新模型 | 否 | 否 | 相同 |

## 三、置信度校准（Jev 的核心价值）

| 置信度档 | 题数 | 准确率 | 含义 |
|---|---|---|---|
| high (≥0.60) | 35 | **100%** | 高置信时零错误，可直接采纳 |
| medium (0.30~0.60) | 21 | 57% | 把握一般 |
| low (<0.30) | 3 | 33% | 不确定 |

**全部 11 个错误都落在 medium/low 档，high 档 35 题零失败。** 置信度是可靠的质量预测器——程序能准确知道"什么时候自己不确定"，这是自回归 JSON 方案完全不具备的能力。

## 四、分类表现

| 类别 | Jev-like | 说明 |
|---|---|---|
| efficiency 牌效率 | 高（high 档全对） | 受限候选 + 进张事实注入 |
| defense 防守 | medium 档为主 | 现物/筋事实已注入，多立直场景仍弱 |
| push_fold 攻守 | 最弱（11 个错误中 7 个在此） | 末巡点差权衡需要更强的推理 |
| value 打点 | 牌选对（Jev 不输出理由故不评理由） | — |

## 五、关于"是否要开思考"

实测结论：**Jev-like 不需要思考**。

| 配置 | 延迟 | 准确率 |
|---|---|---|
| 开思考（128 token 预算） | 4.3s | 80% |
| 关思考 | **1.24s** | 81% |

开思考更慢且不更准。原因：受限候选 + 完整事实注入已把决策空间收窄到无需 CoT；且服务端思考预算占 max_tokens 一半，开思考容易撞输出上限（v1.9.2 教训）。这印证了 Jev 的设计哲学——System One 任务用 System Two 模型是浪费。

## 六、结论与建议

1. **Jev-like 是速度换质量的合理选择**：快 36%、零幻觉、新增概率置信度，代价是准确率 -4 点。
2. **最适合的使用方式**：high 置信档（约 60% 的局面）直接秒回且 100% 准；medium/low 档在 UI 标注"把握一般/较低"，用户可自行复核。
3. **若要追平准确率**：可对 medium/low 档升级到结构化模式复核——但会把这些局面从 1.2s 变成 8s，与"只要打什么牌、要快"的诉求冲突，故默认不启用。
4. **未采用真 Jev 模型的原因**：真 Jev 是闭源托管 API（外网不通），RLCD 训练需 torch/trl/数周算力；而现有 strata 已提供等价的 `allowed_token_ids + logprobs` 原语，无需训练、无需停服务。
